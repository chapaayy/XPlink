# Жизненный цикл ключей — этап 2

1. **Инициализация устройства.** После Matrix password login сервер выдаёт access token и уникальный device ID. Клиент вызывает `initRustCrypto`; приватные Olm/Megolm ключи хранятся в browser IndexedDB. Одновременно два криптоклиента в одной origin не допускаются Web Locks.
2. **Первичная настройка.** Пользователь явно выбирает «Создать recovery key» и вводит пароль для Matrix UIA. `createRecoveryKeyFromPassphrase()` без пароля создаёт случайный recovery key; затем вызывается `bootstrapSecretStorage({setupNewKeyBackup:true})` и `bootstrapCrossSigning`. Существующее secret storage нельзя незаметно перезаписывать.
3. **Предъявление ключа.** Закодированный recovery key показывается только в браузере; пользователь сам должен сохранить его в надёжном внешнем месте. Ключ не записывается в storage, не включается в логи/телеметрию и не отправляется нашему API. Скопированная строка не передаётся тесту через stdout.
4. **Новое устройство.** После нового логина пользователь вводит recovery key. `decodeRecoveryKey` проверяет его формат, затем штатный Crypto API получает приватные cross-signing ключи из зашифрованного серверного secret storage; `loadSessionBackupPrivateKeyFromSecretStorage` и `restoreKeyBackup` восстанавливают сохранённые Megolm-сессии. При неудаче доступный в памяти ключ стирается.
5. **Проверка личности.** Для непривязанного доверенного устройства и собеседника доступен SAS — проверка совпадения чисел/эмодзи людьми на двух экранах. Кнопка подтверждения никогда не нажимается автоматически.
6. **Смена identity.** `getUserVerificationStatus().needsUserApproval` вызывает предупреждение и отказ от отправки, пока не выполнена реальная проверка или сознательное решение пользователя.
7. **Отзыв устройства.** `MatrixClient.deleteDevice` с password UIA отключает серверную сессию. Данные, которые устройство уже успело расшифровать и сохранить локально, нельзя изъять с него.
8. **Исключение участника.** Сервер проверяет право kick. После успешного kick клиент сбрасывает исходящую Megolm-сессию через `forceDiscardSession`; SDK должен распределить новый сеансовый ключ оставшимся членам комнаты. Отзыв прошлых ключей невозможен.

**Важные ограничения:** backup может быть не полностью синхронизирован немедленно после отправки; нужно дождаться выгрузки. Резервная копия ключей не заменяет бэкап сервера. Вторая вкладка той же origin пока показывает блокировку, чтобы не повредить IndexedDB; полноценное одновременное управление — отдельный security design. Согласование смены состава и все edge cases требуют реального тестирования.
